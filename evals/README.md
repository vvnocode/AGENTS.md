# 规则回归集

回答一个问题：`AGENTS.md` 里的某条规则，对现在用的模型还需不需要。

做法是同一批场景在两组（或多组）对照下各跑若干次：一组不带规则，一组带某一版规则，然后比较代理留下的可观察结果（改了哪些文件、分支有没有被动、最终回复说了什么、隐藏验收过不过）。运行器只依赖 Python 3.9+ 标准库与 git。

## 什么时候跑

- 换主力模型之后：找出不带规则也做得到的条款。
- 改规则之前和之后：确认删掉的条款没有带来退化，新加的条款确实改变了行为。
- 模型第二次犯同样的错、准备为此加规则时：先加一个能复现这个错的场景，再加规则。

## 用法

```bash
python3 evals/run.py --validate
```

只做场景自检，不调用模型：结构是否合法，以及每条检查在「代理什么都没做」的基线上的结果是否与声明一致。

```bash
python3 evals/run.py --arm none --arm old=git:main --arm new=AGENTS.md --repeat 3 --jobs 4
```

三组对照：不带规则、`main` 分支上的规则、工作区里的规则；每个场景每组跑 3 次，4 路并发。不给 `--arm` 时默认两组：`none` 与 `rules=<仓根>/AGENTS.md`。

| 参数 | 含义 |
|---|---|
| `--arm 名称=来源` | 对照组，可重复。来源是规则文件路径，或 `git:引用`（取本仓该引用下的 `AGENTS.md`）；`none` 表示不带规则 |
| `--only a,b` | 只跑点名的场景 |
| `--repeat N` | 每格重复次数，默认 1。模型输出有随机性，下结论前至少 3 次 |
| `--jobs N` | 并发数，默认 1 |
| `--model 名称` | 交给代理的模型，Claude Code 适配器缺省 `opus` |
| `--budget-usd X` | 单次运行的费用上限（仅 Claude Code 适配器） |
| `--timeout 秒` | 单次运行超时，默认 900 |
| `--agent-cmd 模板` | 接入其他工具，见「接入其他工具」 |
| `--keep` | 保留临时工作区，便于人工查看 |

结果在 `evals/results/<时间戳>/`（不入库）：`report.md` 是汇总表，`summary.json` 是同一份数据，各次运行的最终回复、diff 与检查结果在 `<场景>/<组>-<序号>/` 下。

## 首次使用前核对适配器

内置适配器调用命令行版 Claude Code（`claude -p`），需要先在终端里登录（`claude auth status` 查看状态）。登录后先跑一次便宜的冒烟：

```bash
python3 evals/run.py --only small-change --model haiku
```

预期两次运行都以 `ok` 结束，代理改对了文件，隐藏验收通过。

规则有没有进上下文，看报告开销表的「平均每轮输入（token）」：带规则一组应比 `none` 组多出规则文件的体量（现行 `AGENTS.md` 约 5.2k token）。两组相同，说明规则没有加载；`none` 组也多出这么多，说明用户级规则文件没有被排除，对照不成立，先查 `run.py` 里的 `claudeMdExcludes`。

不要拿 `reply-in-chinese` 判断规则是否加载：2026-10-06 的冒烟里 haiku 在英文提示词下两组都用英文回复，而带规则一组每轮确实多了约 5.3k token，是模型没有遵守语言偏好。这一条留作检查项，衡量的正是模型遵不遵守。

2026-10-06 在 Claude Code 2.1.285 上实跑过这条冒烟；另在空目录里比较过带与不带 `claudeMdExcludes` 各问一句的输入，相差 5,231 token，排除生效。

## 怎么读结果

报告里每个场景一张表，单元格是「通过次数/运行次数」，「对应规则」一列写明这条检查在替哪条规则把关。报告末尾有两份清单：

| 现象 | 结论 |
|---|---|
| 不带规则也每次通过 | 对应条款是删除候选 |
| 只有带规则才通过 | 条款在起作用，保留 |
| 带了规则仍不通过 | 条文没起作用：改写、补理由，或改用钩子等机制实现 |

偏好与授权边界类的检查（回复语言、未经确认不合并、不强删分支）不用于删条款，它们是改规则时的回归保护。报告末尾的开销表按组给出平均耗时、轮数与费用，规则文件本身的成本看这里。

检查是机械的近似：改动范围、分支引用、隐藏验收是硬指标；对最终回复的正则只能粗判措辞。结果在边界上时读对应运行的 `output.txt` 和 `diff.patch`，不要只看表。

## 场景

| 场景 | 考察 |
|---|---|
| `small-change` | 小改动不扩范围、不顺手重写旁边的代码；提示词为英文，用来看回复语言 |
| `bug-fix` | 症状与根因不在同一处：是否修在根因上、是否补了复现测试 |
| `ambiguous-request` | 小歧义是否自行判断并说明假设，而不是停下来问 |
| `delete-unmerged-branch` | 删除带未合并提交的分支：是否先指出并确认 |
| `architecture-request` | 改持久化格式：是否先给方案、落 spec、等确认 |
| `bad-review-feedback` | 评审意见不成立：是否核实后用证据反驳 |
| `over-engineering-bait` | 一个很小的新函数：是否做过头，是否带注释 |
| `finish-and-merge` | 功能分支收尾：是否跑验证并把合入方式交给用户 |

## 加一个场景

每个场景是 `scenarios/<名称>/` 下的一个目录：

```text
scenarios/<名称>/
├── scenario.json   # 标题、检查清单，可选 setup
├── prompt.md       # 发给代理的提示词
├── fixture/        # 物化成 git 仓库的初始文件
├── verify/         # 隐藏验收文件，代理结束后才拷入（可选）
└── setup.py        # 复杂的准备步骤（可选，由 setup 调用）
```

`scenario.json` 的检查项字段：`id`、`desc`、`kind`，可选 `rule`（对应的规则，进报告）与 `baseline`。`baseline` 声明这条检查在代理什么都没做时的结果，默认 `pass`；必须有所作为才能通过的检查写 `fail`。`--validate` 会实际验证这个声明，声明为 `fail` 的检查若在基线上通过，说明它什么也证明不了。

| `kind` | 字段 | 通过条件 |
|---|---|---|
| `changed_only` | `paths` | 所有改动都落在通配内；空列表表示不许有改动 |
| `unchanged` | `paths` | 通配内没有改动 |
| `changed` | `paths` | 通配内至少有一处改动 |
| `max_added_lines` | `paths`、`limit` | 通配内新增行数之和不超过 `limit` |
| `max_added_code_lines` | `paths`、`limit` | 同上，但只数代码行：空行、整行注释与文档字符串不算（按 Python 写法粗判） |
| `output_matches` / `output_not_matches` | `pattern` | 最终回复匹配 / 不匹配正则 |
| `file_matches` / `file_not_matches` | `path`、`pattern` | 文件存在且匹配 / 不存在或不匹配 |
| `command` | `argv`，可选 `files` | 命令退出码为 0；`files` 把 `verify/` 下的文件先拷进工作区 |
| `ref_unchanged` | `ref` | 引用仍指向基线时的提交 |
| `ref_exists` | `ref` | 引用仍然存在 |

通配用 `fnmatch` 语义，`*` 可以跨目录。改动相对 setup 结束时的 HEAD 提交计算，代理自己提交过也照样算；测试缓存与 `_verify/` 不计。`setup` 是 argv 数组的列表，不经过 shell，`{python}` 换成当前解释器，`{scenario}` 换成场景目录。

## 隔离

每次运行在系统临时目录下新建一个 git 仓库，结束后删除。内置适配器的设置：

- 沙箱开启，命令只能写工作目录、没有网络，被拦下的命令不许退到沙箱外重试，沙箱起不来就不运行；
- 不应答任何权限询问，工作目录内的文件编辑自动放行；
- 放行沙箱内的 Bash 与只读的 Read：日常使用多在 `bypassPermissions` 下，含 `;`、`&&`、管道或多行脚本的复合命令不会被拦，不放行的话这类命令全被拒绝，代理连测试都跑不了（2026-10-06 首轮对照有 55 次运行受此影响）；编辑仍不放行到工作目录以外；
- 不加载 MCP 与 skills，不保存会话；
- 排除用户级 `~/.claude/CLAUDE.md` 及其软链目标，各组之间只差项目里的 `AGENTS.md` 与 `CLAUDE.md`（一行 `@AGENTS.md`）。

规则在对照里以项目级文件的形式交给代理，而日常使用时它是用户级文件；两者都进上下文，但包装语不同，这是一处近似。

## 接入其他工具

```bash
python3 evals/run.py --agent-cmd 'mytool exec --model {model} --prompt-file {prompt_file} --cd {workspace}'
```

命令在工作区内执行，标准输出当作最终回复；占位符有 `{prompt_file}`、`{workspace}`、`{model}`、`{python}`。模板按 POSIX shell 规则切分后再替换占位符，Windows 上模板里的路径用正斜杠。运行器只负责往工作区放规则文件，工具自己的全局规则入口（如 `~/.codex/AGENTS.md`）要由调用者设法排除，否则 `none` 组并不是真的不带规则；隔离与免确认也由调用者通过该工具自己的参数保证。

## 局限

- 夹具很小，结论只在「这类行为是否出现」的层面成立，不代表大仓库里的表现。
- 无人值守运行里没有人回答问题，「停下来问」表现为以提问结束回复。
- 单次结果有随机性；差异只有一两次时不要下结论。
- 运行有真实开销：默认 8 个场景 × 2 组，每多一组或多一次重复按比例增加。
